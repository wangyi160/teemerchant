# Merchant-service OAuth

[简体中文](OAUTH.md) | **English**

Authorization and renewal run in the local merchant HTTP service. Provider endpoints and public CLI client IDs are defined in `oauth_service.py`, retaining previously reviewed Codex, Claude Code and Grok CLI parameters. Browser forms have separate OAuth / JSON tabs. OAuth fills a draft only; saving requires a successful connection test.

OpenAI uses Codex device-code authorization. Through the account proxy, the service requests a code from `/api/accounts/deviceauth/usercode`; the user enters it at `https://auth.openai.com/codex/device`. The service polls `/api/accounts/deviceauth/token` at the official interval, at least five seconds. 403/404 means authorization is pending, with a maximum wait of 15 minutes. Approval returns an authorization code and PKCE verifier for exchange at `/oauth/token`, using redirect URI `https://auth.openai.com/deviceauth/callback`. There is no localhost listener, manual callback input or automatic browser-PKCE fallback. Device login must be enabled in ChatGPT security settings or workspace permissions. References: [official authentication guide](https://learn.chatgpt.com/docs/auth#preferred-device-code-authentication-beta) and [Codex implementation](https://github.com/openai/codex/blob/main/codex-rs/login/src/device_code_auth.rs).

Claude and Grok use independent PKCE S256 verifiers and state, with an additional Grok nonce and ten-minute expiry. Grok requires the complete localhost callback URL matching the registered redirect URI and state. Claude accepts the official authorization code or code#state. Sessions bind to the browser session, merchant identity, Router and pool. Device-code polling does not hold the service state lock. Cancellation, lost authentication or configuration changes prevent later exchange/delivery; code-exchange requests are not replayed automatically. Errors, cancellation and expiry clear server drafts. Credentials can be retrieved only once, and polling does not reveal tokens.

Device-code requests/polls, code exchanges and all three providers' refresh requests use the configured HTTP(S), SOCKS5h or VLESS account proxy, with HTTPS validation, no redirects, no environment-proxy substitution and no direct fallback. Errors exclude upstream response bodies and tokens.

Refresh tokens remain only in the encrypted merchant store. Before renewal, the service persists intent; on success it saves complete rotated credentials before checking authentication and uploading an access-only projection. Progress tracks **refresh → check new token → upload Router**. Failed steps retry after 30, 60, 120 and 300 seconds, sharing four retries across the cycle; completed steps are not repeated. Lost refresh responses or restart during renewal follow the same policy, so an uncertain remote result may lead to another refresh request; provider refresh idempotency is not guaranteed. Exhaustion pauses the account for merchant retry/reauthorization. Manual refresh resumes the failed step immediately and resets the budget. Upload failure does not re-refresh an already obtained token.

`account_auth.py` queries official model endpoints through the account proxy to check credential acceptance, without inference or a separate per-account catalog. New credentials, proxy changes or manual retries trigger checks. 401, 403, 429 and network failures are recorded distinctly, without raw errors/secrets in state. `account_sync` pauses per deployment and binds status to local credential/proxy digests. Failed accounts are excluded from subsequent automatic uploads and Router recovery, while healthy accounts continue independently.

Router advertises `merchant.credential_protocol: access-token-only-v1`. Incompatible Routers are rejected before account upload. Full configuration/test requests omit refresh tokens. Incremental `PUT /merchant/accounts/access` contains `runtime_id`, account alias, `expected_access_sha256` and `credential`. Identical retries do not increase account versions; different runtimes, stale-digest overwrites and refresh fields are rejected.

Before upgrading from old Router-managed refresh, first save the latest credentials from the old Router, then stop old clients and upgrade Router. An old Router may already have rotated refresh tokens; starting renewal with an older local copy is unsafe. Access-token-only accounts may instead be retained and reauthorized manually at expiry.

Tests cover device-code requests, poll intervals and pending 403/404, errors/timeouts, cancellation/identity switching/logout during authorization, single exchange/retrieval, device UI and test-before-save. They also cover local session/CSRF/Host isolation, callback state, PKCE, provider refresh parameters, rotated-credential persistence, interrupted-intent handling, access-only projection and controlled incremental sync. Real provider login requires merchant interaction in the browser; tests do not claim real authorization.
